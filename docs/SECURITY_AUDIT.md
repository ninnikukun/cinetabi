## 中程度の指摘

### 1. `/api/tmdb`・`/api/cinemas` にレート制限・オリジン制限が無く、鍵の使用量を第三者に消費されうる

**該当箇所**: `api/tmdb.js`, `api/cinemas.js`

両エンドポイントは認証・レート制限・Origin/Referer検査のいずれも行っていません。

- `/api/tmdb` は `TMDB_API_KEY` を使ってTMDBへ中継しています。誰でも（自分のサイトを持たない第三者でも）このエンドポイントを直接叩けば、あなたのTMDB APIキーの利用枠を消費できます。
- `/api/cinemas` は `ORS_API_KEY`（OpenRouteService、有料枠のある鍵）を使って徒歩時間を計算します。同様に第三者が大量に叩けば、この鍵の利用枠が消費されます。
- どちらもCORSヘッダーを明示的に絞っていないため、他サイトの `<img>` や `fetch` からの呼び出しも（レスポンスを読めなくても）サーバー側では実行されてしまいます＝リクエスト自体はコスト・枠を消費します。
- `/api/cinemas` はさらにNominatim・Overpassという無料の共有インフラも中継しており、悪用されるとそれらのサービスから自分のVercelのIPがブロックされるリスクもあります。

**推奨対応（例）**: Vercelの IP/レート制限（Edge Configやミドルウェア）、簡易的なトークンチェック、あるいは1日あたりの呼び出し回数を`Cache-Control`とセットでCDNキャッシュに寄せる、など。個人利用規模なら優先度は高くありませんが、公開URLである以上ゼロにはできません。

### 2. セキュリティヘッダーが未設定

**該当箇所**: `vercel.json` が存在しない（リポジトリ全体を確認済み）

Content-Security-Policy、X-Frame-Options（またはCSPの`frame-ancestors`）、X-Content-Type-Options、Referrer-Policy、Permissions-Policy のいずれも設定されていません。

- クリックジャッキング対策が無いため、悪意あるサイトが `<iframe>` でこのアプリを埋め込み、ログインボタンやカメラ許可ダイアログを透明化して誤クリックを誘発する余地が理論上あります。
- カメラ機能（`getUserMedia`）を実装済みのため、`Permissions-Policy: camera=(self)` のような明示制限が無いのは特にこのアプリに関係する項目です。
- 現状はReactのデフォルトエスケープでXSSは起きにくい作りですが、CSPが無いため「万一XSSが入った場合の被害範囲を抑える」多層防御が効いていません。

**推奨対応**: `vercel.json` に `headers` 設定を追加する（低コストで対応可能）。

### 3. 共有リンク（`/s#…`）に記録の本文（note）が平文相当（base64）で埋め込まれるが、表示するルートが実装されていない

**該当箇所**: `src/App.jsx` の `ShareSheet`（`link` の生成箇所、`btoa(...)` で `/s#` に埋め込む処理）

```js
const payload = btoa(unescape(encodeURIComponent(JSON.stringify({ t:movie.title, n:movie.note, f:movie.filmId, u:user?.name }))));
return origin + "/s#" + payload;
```

- ユーザーが書いた個人的な感想文（`note`）がbase64（暗号化ではなく単純なエンコード）で丸ごとURLに入ります。base64は誰でも一瞬でデコードできるため、実質「平文をURLに載せている」のと同じです。
- リポジトリ内を検索した限り、パス `/s` を受け取って中身を表示するルート／コンポーネントが見当たりませんでした。生成された共有リンクは現状どこにも着地しない可能性があります。
- この状態でリンクがコピー・共有（メッセージアプリやメモアプリの送信履歴・クリップボード履歴など）されると、実装が完成していないにもかかわらず個人の感想文だけがURLとして端末間を移動することになります。
- なお `docs/IMPLEMENTATION_SPEC.md` §4にも「投稿リンクを非フォロワーが踏んだ場合の見え方は未確定・OGP実装は着手しないこと」という同種の懸念がすでに記録されており、本件はその未決事項と地続きの問題です。

**推奨対応**: `/s` のビューアーを実装するまでは、共有リンクの生成自体を一時的に無効化する（画像カードの保存・共有のみに絞る）のが安全です。実装する際は、埋め込む項目を必要最小限にし、「誰でも読める」ことを前提にした文言・UIにしてください。

### 4. `records.image`（写真データ）にサーバー側のサイズ・形式チェックが無い

**該当箇所**: `src/App.jsx` の `addMovie` → `toRow()` → `supabase.from("records").insert(...)`

写真はクライアント側で `resizeImage()` / カメラの `cropToAspectDataUrl()` により縮小されてからbase64として送信されますが、これはあくまでクライアント側の制御です。ログイン済みユーザーがブラウザの開発者ツールやAPIを直接叩けば、リサイズをバイパスして任意サイズのbase64データを `records.image` に入れられます。

- 影響は基本的に「自分の行を肥大化させる」に留まり（RLSにより他人の記録は書き換えられない）、直接の情報漏えいではありません。
- ただしDBコストの増大や、将来的な一括エクスポート・バックアップサイズの肥大化、極端に大きい値を入れられた場合のクエリ・表示側の予期しない負荷につながる可能性があります。

**推奨対応**: `records` テーブルに `image` のサイズ上限（例: `check (length(image) < 2000000)` 等）を設けるか、既存ロードマップ通りSupabase Storageへの移行時に、Storage側の `file_size_limit` / `allowed_mime_types`（`avatars` バケットで既に採用している仕組み）で制御するのが望ましいです。

## 低程度の指摘

### 5. コアテーブル（`profiles`・`records`）のRLS定義がリポジトリにバージョン管理されていない

**該当箇所**: リポジトリ全体（`supabase/` には `stage2_follows.sql`・`stage2_follows_fix1.sql`・`avatar_upload.sql` のみ存在）

`CLAUDE.md` に「RLSで『本人のみ』＋（ステージ2以降）『承認済みフォロワーも閲覧可』」という記載はありますが、その**本人のみ**を実現しているはずの `profiles`・`records` 自体の初期RLSポリシー（`create table` や最初の `create policy` を含む）を定義したSQLがリポジトリ内に見つかりませんでした。Supabaseダッシュボードから直接設定された可能性が高いです。

- 現在の設定が本当に「本人のみ」になっているかどうかは、コードレビューだけでは検証できません（Supabase側の実際の設定を直接確認する必要があります）。
- 将来別の担当者が触る場合、根拠となるSQLが無いため意図せず緩めてしまうリスクがあります。

**推奨対応**: Supabaseダッシュボードの現在のポリシーを `pg_dump` やダッシュボードのSQL表示機能でエクスポートし、`supabase/` 配下に基礎スキーマとして追加しておくことを推奨します（今回のスコープ外のため実施していません）。

### 6. ローカルに `.env.bak_utf16` が残っている

**該当箇所**: リポジトリ直下（gitには含まれていないことは確認済み・`.gitignore` で `.env.*` を除外済み）

`CLAUDE.md` に記載のあるUTF-16保存トラブルの際にできたと思われるバックアップファイルがまだ残っています。git管理外なのでリポジトリ経由の漏えいリスクはありませんが、シークレット（Supabase鍵等）を含むファイルが必要以上に長く平文でディスク上に残る状態です。

**推奨対応**: 内容を確認の上、不要であれば削除してください（本レポートでは内容の中身は読んでいません）。

### 7. 写真データをオブジェクトストレージではなくDBのテキスト列にbase64で保存している

**🔧 実装済み・適用待ち（2026-08-13、`feature/record-photos-storage`ブランチ）**

`records.image` を、非公開Storageバケット（`record-photos`）内の相対パス参照に変更する実装をブランチ上で完了。アクセス制御はサーバー側の関数を新設せず、`storage.objects` のRLSに `records` と同じ「本人 or 承認済みフォロワー」条件を設定し、認証済みブラウザから直接 `createSignedUrl`（期限付き）を発行する設計。実装の詳細は `docs/IMPLEMENTATION_SPEC.md` §9 を参照。

- ⚠️ 本番Supabaseプロジェクトへの `record_photos_storage.sql` の適用、および「承認済みフォロワーが署名付きURLを発行できるか」の実機確認（本人だけでなく2アカウントでの検証が必須）は未実施。これが確認できるまで、この項目は完了とみなさないこと。
- ⚠️ `records_image_path_guard.sql` は既存base64データの移行が全ユーザー分完了するまで適用しないこと。当初「該当2件のみ・削除して撮り直す」想定だったが、実際は15件・自分以外に3ユーザー分の実データがあることが判明したため、`src/App.jsx`の`migrateLegacyBase64Photos()`が各ユーザーの次回ログイン時に自動移行する方式に変更した（詳細は`docs/IMPLEMENTATION_SPEC.md`§9）。全員がアプリを開き終え、`select count(*) from public.records where image like 'data:%';`が0件になったのを確認してから適用すること。

### 8. `request_follow` RPCに呼び出し頻度の制限が無い

**該当箇所**: `supabase/stage2_follows.sql`

ID・表示名の組が一致しない限り常に同じ `not_found` を返す設計自体は列挙攻撃への対策として適切です（誤り箇所を区別できないよう`and`条件で1クエリにまとめている）。ただし呼び出し自体の頻度制限は無く、大量呼び出しによるDB負荷は理論上可能です。実害は小さいと判断し低評価としています。

## 確認したが問題が無かった項目

- **シークレットの漏えい**: `.env`／`.env.*` はgit管理外。過去のコミット履歴にも含まれていない。コード内にハードコードされたAPIキー・シークレットも無し。
- **クライアントに露出する環境変数**: `TMDB_API_KEY`・`ORS_API_KEY` はサーバー側（`api/*.js`）でのみ読まれ、`VITE_`プレフィックスが無いためクライアントバンドルに含まれない。`VITE_SUPABASE_ANON_KEY` は設計通り公開鍵（RLSで保護）。
- **XSS**: `dangerouslySetInnerHTML`・`innerHTML`・`eval`・`new Function` の使用なし。ユーザー入力（記録文・表示名等）はすべてReactの通常のテキスト描画で自動エスケープされている。
- **依存パッケージの既知脆弱性**: `npm audit --omit=dev` で0件。
- **SQLインジェクション**: `api/cinemas.js`・`api/tmdb.js` とも外部URLへのパラメータは `encodeURIComponent` を通しており、DB操作はSupabaseクライアント（パラメータ化）経由のみ。生SQL文字列結合は無し。
- **フォロー機能の列挙攻撃対策**: `request_follow` はID・名前の一致を1クエリのAND条件にまとめており、片方だけの正誤を外部から判別できない設計になっている。
- **Service Workerのキャッシュ範囲**: `/api/` パスとクロスオリジンリクエストは明示的にキャッシュ対象から除外されており、他人の検索結果や認証情報をキャッシュ経由で誤って返す作りにはなっていない。
- **Storageのアクセス制御**: `avatars` バケットは書き込みを本人のファイル名（`{uid}.jpg`）に限定し、匿名ユーザーの書き込みも拒否。サイズ上限・MIMEタイプもバケット側で強制されている。
