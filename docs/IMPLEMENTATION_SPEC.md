**対象**: シネたび (CINETABI) — 記録画面・詳細画面のUI刷新

**参照モックアップ（デザイン確定済み）**:

- `cinetabi-final-mockup-v2.html`（記録画面①＋詳細画面BeReal型・基本形）
- `cinetabi-detail-links-mockup.html`（詳細シートに外部リンク追加版・**最終形はこちら**）

## 1. 前提・方針

- ポスター画像・ユーザー投稿写真は、どちらも **9:16の縦比率** で統一する（現行の16:9横フィルムコマから変更）。
- **写真の投稿を必須にする。** ポスターのみの記録は作れないようにする（詳細は §5 参照）。
- 既存のNEGA（フィルムネガ風）のトーン・カラーは踏襲する。新しいUIでもスプロケット穴等の装飾は使わないシンプルな方向。

---

## 2. 記録画面（一覧・タイムライン）

### レイアウト

- 1エントリー = 横に並んだ2枚の9:16画像（左：ポスター／右：ユーザー写真）。
- 画像間は1px程度の細い継ぎ目線（`rgba(255,255,255,.15)`）のみ。ラベルテキスト（「POSTER」「PHOTO」等）は **表示しない**。
- 画像ペアの下に、作品タイトル（太字）と日付・劇場名（小さめ・muted色）を1行ずつ。

### 実装メモ

- 既存のフィルムストリップ表示（16:9横コマ・スプロケット穴・月の継ぎ目）はこの一覧では使わない。単純なリスト（縦スクロール、エントリーごとにカード）に置き換える。
- CSS: `aspect-ratio: 9/16` を各画像に指定し、`display:flex; gap:2px` で2枚を横並びに。

## 3. 詳細画面

### 基本構造（BeReal風）

- メインエリアは画面いっぱいの写真（9:16、フルブリード）。
- 左上に小さいインセット枠（画面幅の約34%、9:16）でポスターを表示。タップするとメインとインセットの中身が入れ替わる（写真⇄ポスター）。
- ラベルテキスト・星評価は **表示しない**。

### 詳細シート（タイトル・記録文・外部リンク）

- 通常時は非表示。画面下端に小さいハンドル（バー＋「詳細」の矢印アイコン、上下にゆっくりバウンドするアニメーション）だけ見せる。
- 画面を下方向にスワイプ（ドラッグ）すると、下からシートがせり上がって表示される。
  - ドラッグ量が一定以上（目安40px）でシートが開く。
  - シートをタップすると閉じる。
  - アニメーションは `transform: translateY()` + `transition: .28s cubic-bezier(.22,.68,0,1)` 程度の軽いイージングで。

シート内の内容（上から順）:

1. 作品タイトル（太字、白系）
2. 日付・劇場名（小さめ、mutedカラー、date部分はmonoフォント推奨）
3. 記録文（メモ本文）
4. 外部リンクチップ（映画.com／Filmarks、それぞれpill形のボタン、外部リンクアイコン付き）

### 外部リンクチップ

- 「映画.com」「Filmarks」の2つを横並びで、記録文の直下に配置。
- クリックで新規タブ／外部ブラウザで該当作品の検索結果ページへ遷移。
  - URL方式：作品タイトル（＋可能なら公開年）でその場でクエリを組み立てる**検索リンク方式**を推奨。
    - 映画.com検索例: `https://eiga.com/search/{URLエンコードしたタイトル}/`
    - Filmarks検索例: `https://filmarks.com/search/movies?q={URLエンコードしたタイトル}`
  - 作品IDを事前に紐付ける精度の高い方式は将来検討（今回は対象外）。

今回のスコープではないが、詳細画面と地続きの機能として設計済み。実装フェーズが来たら以下を参照：

## 5. 写真必須化

- 投稿（記録追加）フローで、写真の選択をスキップできないようにする。
- ポスターのみでの投稿は不可。
- 写真の追加は `<input type="file" accept="image/*">`（`capture`属性なし）を直接開く形にしており、OS標準の選択画面（「写真を撮る」「フォトライブラリ」等）がそのまま表示される（§6参照）。選んだ画像は9:16に中央クロップ・縮小してから保存する。
- 保存先はDBの `records.image` 列そのもの（base64）ではなく、Supabase Storageの非公開バケット。`records.image` にはStorage内の相対パスだけが入る（§9参照）。
- ただし§5適用前に作られた記録（写真が無いもの）は既存データとして残るため、表示側のフォールバック（一覧では右側を無地に、詳細画面ではポスターをメインにしてワイプを出さない）は維持する。新規記録では発生しないが、削除はしないこと。

## 6. 写真の追加手段（サイト内カメラ撮影は不採用・撤回）

**当初の計画（不採用）**: 投稿フローで端末のカメラアプリに遷移させず、サイト内にライブプレビューを表示してその場で撮影できる `CameraCapture` コンポーネント（画面いっぱいのライブプレビュー・9:16ガイド枠・フロント/バック切り替え・シャッター・確認画面）を実装した。

**撤回した経緯**: 実際に使ってみると、写真追加ボタンを押すたびに毎回このカメラUIが最初に開き、ライブラリからの選択がその中の小さい「アルバム」ボタンとしてしか出せない状態になっていた。OS標準の選択画面（写真を撮る／ライブラリから選ぶを最初から両方提示してくれるもの）を経由する方が使い勝手が良いと判断し、`CameraCapture` コンポーネントは削除して `<input type="file" accept="image/*">` を直接開く実装に置き換えた（§5参照）。

**アバター機能（§7）でも元々このコンポーネントは流用しない判断だったため、他に利用箇所は無く、削除して問題なかった。**

技術的な知見（今後似た機能を検討する際の参考）:
- `capture="environment"` を `<input type="file">` に付けると、ブラウザによってはカメラ起動のみに固定され、ライブラリからの選択ができなくなる。OS標準の両方の選択肢を残したい場合は`capture`属性を付けないこと。
- サイト内カメラ実装時のポイント（再度実装する場合の参考）: `getUserMedia({ video: { facingMode }, audio: false })`、`<video autoplay playsinline muted>` が必須、HTTPS環境限定で動作、フロントカメラのプレビューは`scaleX(-1)`で鏡像補正するが保存データは正像にする、等。

## 7. プロフィール画像アバター機能

### 背景

現状、ユーザーのアバターは画像ではなく「表示名の頭文字を入れたアンバー色の丸」（アプリヘッダー／フレンドの記録画面ヘッダー／フォロー画面／フォロー一覧、の4箇所で共通）。これを画像アップロード対応にする。

### 対応範囲（実装済み）

- `profiles` テーブルに `avatar_url` 列を追加。
- Supabase Storageに画像保存用のバケット `avatars` を新設（公開読み取り可・書き込みは本人のみ・匿名ユーザーは書き込み不可）。
- プロフィール編集画面（フォロータブのMY PROFILEカード）に「画像を選ぶ」ボタンを追加。
  - 選択後、クライアント側で正方形クロップ＋400px程度にリサイズしてからアップロード。
  - 「その場で撮る」専用UIは見送り。OS標準のファイル選択シートから「写真を撮る」も選べるため、実用上はこれで十分と判断（§6のカメラコンポーネントは流用しない）。
- 既存の「頭文字の丸」表示（アプリヘッダー／フレンドの記録画面ヘッダー／フォロー一覧／詳細画面の上部黒帯／MY PROFILEカード）は共通の `Avatar` コンポーネントに統一済み。`avatar_url` があれば画像、無ければ頭文字の丸を表示。
- フォロー承認待ちの相手は、承認済みと見分けがつくよう画像化せず頭文字の丸のまま（意図的な仕様）。

### 技術メモ

- アップロード画像は正方形にクロップしてから保存する（表示側での縦横比のズレを防ぐため）。
- ファイルサイズ・容量への配慮として、アップロード前にクライアント側でリサイズ（長辺400px程度で十分）してからアップロードする。
- Supabase Storageのパスは `avatars/{user_id}.jpg` のように固定パスにし、上書き保存にすることで、DB側は `avatar_url` を都度更新するだけで済むようにする（同名ファイル上書きの場合はCDNキャッシュ回避のためクエリパラメータでバージョン管理する等の対応が必要になる場合あり）。

### 想定変更ファイル

- DBマイグレーション：`profiles` テーブルへの列追加、Storageバケット作成・ポリシー設定
- プロフィール編集コンポーネント：画像選択・撮影・アップロードのUI追加
- アバター表示箇所（4箇所＋詳細画面ヘッダー）：画像 or 頭文字丸の出し分けロジック

## 9. おもいで写真のSupabase Storage移行（docs/SECURITY_AUDIT.md 項目7）

### 背景

これまで `records.image` にbase64のdata URLをそのままDBに保存していた（§5）。件数・サイズが増えるとDBの行サイズ・バックアップ容量を圧迫するため、実体はSupabase Storageの非公開バケットに置き、`records.image` には「バケット内の相対パス」だけを保存する形に変更した。

### 設計判断：署名付きURLの発行にサーバー側の関数を使わない

当初は「Edge Function経由で署名付きURLを発行し、その中で`records`と同じ権限チェックを行う」案があったが、以下の理由からRLSのみで完結させる設計に変更した。

- Supabaseの `createSignedUrl` は `storage.objects` のRLS（SELECT）に従う。`records` と全く同じ「本人 or 承認済みフォロワー」の条件をStorage側のポリシーにも設定すれば、権限チェックのロジックを重複実装せずに済む（RLSが唯一の判定ロジックになる）。
- このプロジェクトにはSupabase Edge Functions用のCLI/デプロイ環境が無く、新設すると別のデプロイパイプラインが増える。Vercelの`api/*.js`だけで完結する既存の構成に馴染まない。
- 結果として、ブラウザの認証済みSupabaseクライアントから直接 `supabase.storage.from('record-photos').createSignedUrl(...)` を呼ぶだけで完結する（アバター機能と同じ「クライアント→Supabase直」のパターン）。

### 実装内容

- 新規バケット `record-photos`（非公開・`file_size_limit: 2MB`・`allowed_mime_types: ['image/jpeg']`）。パスは `{user_id}/{ランダムなuuid}.jpg` 固定、上書きはしない（差し替え時は新パスでアップロードし、古いオブジェクトを削除する）。
- `storage.objects` のポリシー（`supabase/record_photos_storage.sql`）：
  - SELECT（署名付きURL発行も含む）：`records.image = 対象パス` を条件に `records` を参照し、本人 or 承認済みフォロワーだけ許可。
  - INSERT/DELETE：`{自分のuser_id}/…` 配下のみ。写真は匿名ユーザーでも必須（§5）のため、アバター（`avatars`）と違い匿名ユーザーの書き込み制限は付けていない。
- `records.image` のサーバー側チェック（`records_image_guard.sql`）は、base64形式の検証だったため実態と合わなくなった。パス形式（`{uuid}/{uuid}.jpg`）を検証する `records_image_path_guard.sql` に置き換えた。
- クライアント側（`src/App.jsx`）：
  - `AddSheet`/`EditSheet` 自体はこれまで通りdataURLを扱う（`LocalApp`＝端末保存モードと共有しているため、Storage関連の処理はここに置かない）。
  - アップロード・削除・署名付きURL発行は `CloudApp` の `addMovie`/`updateMovie`/`deleteMovie`、および `DetailView` の写真取得処理に集約した。
  - `EditSheet` の保存内容は `image` を直接渡す形から `photo: { changed, dataUrl }` に変更した。`movie.image` が実体ではなく署名付きURL（毎回文字列が変わりうる）になったため、値の比較では「変更したか」を判定できないための対応。
  - `records.image` を直接SELECTしていた `DetailView` の一括取得処理を、「パスを取得 → 署名付きURLをまとめて発行」の2段階に変更。
  - `backfillThumbnails`（旧・thumbnail自動補完処理）は `records.image` を直接 `<img>` に読み込む実装だったため、パス移行後は機能しなくなる。既存記録には全件thumbnailが入っている前提で削除した。
  - 共有画像の書き出し（`ShareSheet`の`drawCard`）は、写真が別オリジン（Storageの署名付きURL）になったことで`canvas`が汚染されないよう、読み込み前に `Image.crossOrigin = "anonymous"` を明示した。

### 既存データの移行

当初は該当記録が2件のみという想定で「削除して撮り直す」運用を予定していたが、実際にDBを確認したところ15件・自分以外に3ユーザー（え・ひんと・うなぎ）分の実データがあることが判明し、他ユーザーの投稿を勝手に消せないため方針を変更した。

`src/App.jsx` の `migrateLegacyBase64Photos(uid)` を、`CloudApp` がプロフィール確定後に1回だけ自動実行する形で仕込んである。ログイン中ユーザー自身の `records`（RLSにより他人の行はUPDATE不可のため、これしか選択肢がない）のうち `image` が `data:` から始まるものだけを対象に、Storageへアップロードしパス参照へ書き換える。各ユーザーが次回アプリを開いたタイミングで自動的に自分の分が移行される。

`records_image_path_guard.sql` は、全ユーザー（自分含め4人）がアプリを一度開き終えて `select count(*) from public.records where image like 'data:%';` が0件になったのを確認してから適用すること。適用後、`migrateLegacyBase64Photos` とその呼び出し箇所（`ponytail:` コメント付き）は不要になるので削除してよい。
